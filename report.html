Auditoría técnica de Manus POS

Versión corregida. Auditoría estática y ejecución segura. No se modificó código de producto, configuración, base de datos ni infraestructura. Commit auditado: e93995268c9977a6bdfe35e3ac0bc281c8e45dcd, base origin/develop. Fecha: 2026-09-16.

1. Resumen ejecutivo

Manus POS es un shell Electron que abre la aplicación web. No es POS offline. Electron tiene mecanismos de carga, fallback y recuperación del renderer; el web persiste sesión/contexto/carrito para rehidratar la UI. No hay evidencia de cola local de ventas ni de operación transaccional sin API. El producto auditado es POS/ERP web multi-tenant con facturación, reportes y periféricos. No se auditan funciones que no existen en el repo: surtidores, “Valdia Pro” y gateways de pago.

5. Flujo principal

Electron inicia una URL web. El web hace login/refresh, carga perfil/menu/permisos, selecciona tenant/sucursal/terminal, mantiene carrito y envía operaciones al API. Facturación y reportes viven en servicios separados. Evidencia: desktop/electron/config.ts, web/domains/auth/session-manager.ts:157-179, web/app/[tenant]/pos.

6. Arquitectura

La organización por módulos/features es clara. API usa SQL directo desde servicios/repositorios; no hay ports/adapters uniformes. Esto es deuda de mantenibilidad, no prueba de daño funcional.

7. Electron

Electron es shell online: contextIsolation:true, nodeIntegration:false, sandbox:true en desktop/electron/main.ts:179-184. Preload expone API acotada en desktop/electron/preload.ts:5-21. Tiene single instance, bloqueo de cierre, navegación controlada y recuperación del renderer en main.ts:54,206-229.

8. Fallos y recuperación

Si falla la carga inicial, Electron escribe una página local de conexión interrumpida y reintenta cada 3 segundos (desktop/electron/main.ts:288-317). Si muere el renderer, intenta recargar hasta el límite definido (main.ts:220-229). Si queda no responsivo, solo registra warning (main.ts:235-236). Esto recupera shell/UI; no confirma recuperación de una venta enviada al API.

9. Persistencia para rehidratar

Ya existe persistencia de refresh token en localStorage (web/domains/auth/session.ts:34-50), menú en sessionStorage (web/domains/auth/menu-cache.ts:76-102), contexto POS en localStorage (web/store/pos.ts:140-220) y carrito por tenant/sucursal/terminal/usuario/sesión (web/store/posCart.ts:88-100,211-258). Esto permite rehidratar estado de UI después de reload/reinicio. No es persistencia de transacciones confirmadas.

10. Offline

No se debe llamar offline al producto. La página local de Electron solo informa y espera reconexión. El README marca Offline sync/PWA como pendientes (README.md:57-72). Venta, inventario, facturación y consultas requieren API o no están demostradas sin API.

11. Autenticación y sesión

JWT, tenant_id y sesión activa se verifican (api/src/common/guards/jwt-auth.guard.ts:58-100); refresh rota tokens (api/src/modules/auth/auth.service.ts:307-347). Riesgo P2: refresh persistible en localStorage. La rehidratación mantiene usuario/contexto cuando la llamada de perfil falla, pero permisos se limpian ante error en session-manager.ts:170-179.

12. Multi-tenant

El tenant principal viene del JWT. Terminal devices valida tenant y rol SUPER_ADMIN en api/src/modules/terminal-devices/terminal-devices.service.ts:13-16. La prueba negativa exhaustiva para todos los endpoints queda como verificación recomendada.

13. Ventas

Hay carrito, productos y operaciones de venta. El carrito se persiste por contexto. No hay evidencia de outbox local de venta ni de reconciliación de una solicitud cuyo resultado queda ambiguo después de una caída del API. Idempotencia de creación: NO VERIFICADA.

14. Métodos de pago internos

El frontend valida suma, faltante y sobrepago para métodos configurados (web/modules/shared/payments/payment-allocation.helper.ts:174-192). Reportería agrega pagos por método. No hay gateway de tarjetas, Nequi, Wompi, Bold ni datáfono integrado en el alcance. Por tanto no se reportan defectos de integración inexistente.

15. Facturación electrónica

16. Periféricos

17. Persistencia

18. Sincronización
