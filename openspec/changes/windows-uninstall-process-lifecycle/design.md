## Decisions

### 1. Durable completion and bounded recovery

Proposed parent contract: 0 only for verified completion/no-op, 1 for immediate failure and 2 for accepted asynchronous handoff. The helper and matching operation result decide final completion after parent exit. A synchronous parent wait cannot be introduced while the helper also waits for that parent.

The historical result file and atomic write are candidates. Before recovery, bind operation identity, parent start identity, mode, result path and all managed roots to one trusted installation. Preserve original historical records; in-memory normalization of the narrow legacy completed shape is bookkeeping only.

The historical helper still calls waitForParentExit with INFINITE. Its two-minute stale-result classification is not a helper deadline, process-death proof or concurrency lock. Future design must define bounded waits, single-writer operation handling and safe stale-helper observation. Unknown parent access is not confirmed parent exit.

Completion requires known process, service, payload, shortcut, registry and TEMP observations plus durable persistence. Scheduling TEMP deletion is not proof of deletion. Retry must remain discoverable if cleanup or result persistence fails after payload/registry work. Do not promise atomic rollback after destructive uninstall phases.

### 2. Process ownership, PID reuse and raw execution

The baseline enumerates path-scoped PIDs, then reopens them without start-identity checks. This is a confirmed source gap; terminating an unrelated reused PID is an inferred risk.

Future termination requires a retained handle, verified start identity, exact current image/root and live ownership proof. Vanished processes may be benign only with authoritative absence evidence. Incomplete enumeration or access remains unknown, never known zero. No executable-name or PID-only authorization.

The historical Discover returns Job members when a Job exists and does not inspect raw processes outside that Job. An empty Job cannot prove the managed root has no raw/unowned process. Such coexistence must block deletion without terminating the unowned process.

Missing ownership after normal POS close, crash, logoff or reboot also needs a safe idle/retry contract. Neither a missing Job nor an editable journal proves zero processes. The recovery design for that boundary remains open.

### 3. Job, supervisor and journal security gates

Historical source confirms:
- CreateJobObject receives nil security attributes; no explicit DACL or preexisting-object trust check is demonstrated.
- The Job name is derived from the root in the Local namespace. Session/account access must be proved, not assumed.
- POS starts suspended, joins the Job and resumes. No breakaway or kill-on-close flags are requested for the POS Job.
- The supervisor writes pos-ownership.json beneath StateRoot after starting POS.
- Current managed StateRoot DACL grants SYSTEM/Administrators and LocalService, with no standard-user grant. A standard-user journal failure is inferred; do not solve it by broadening mutable Agent state access.
- launchManagedPOS ignores corrupt journal read errors and accepts a readable active record as handoff without binding it to the new supervisor.
- validatePOSOwnershipJournalIdentity is defined but not used by those production launch paths.
- BootIdentity uses GetTickCount64 and direct equality. A stable, OS-backed boot/session identity mechanism remains to be selected and verified.
- ProcessState polling is not an demonstrated child-exit observer without Wait.
- Errors after resume/journal persistence can leave POS running. Cleanup policy must cover the exact newly created child and handles without affecting unrelated work.
- Supervisor waits for the primary POS process; descendant lifetime, last Job handle loss and child survival need tests.

The journal is historical evidence only. It never authorizes termination or adoption. Supported launch paths must bind root, executable and journal destination before spawning. A preexisting named object must not become authority merely because its name matches.

Default ACL behavior, injected allow/deny seams and source-string assertions do not prove real cross-account authorization. The historical TestPOSSupervisorRestartRefusalIsBounded only measures elapsed time and does not exercise a supervisor restart.

### 4. Elevated roots, reparse points and data policy

Both baseline and candidate accept helper root arguments with incomplete identity binding. The candidate validates result operation/mode but does not establish parity between supplied roots and a trusted installation. Exact-root and reparse protections on --remove-data do not establish equivalent protection for POS payload, Agent payload, result destination or TEMP cleanup.

Future preflight must validate all affected roots and ancestors before mutation, distinguish known managed current junctions from untrusted substitutions, reject volume/share/broad roots and revalidate at the destructive boundary. Concrete handle-based/Windows mechanisms remain implementation design work; no broad takeown or ACL weakening is approved.

Standard uninstall preserves existing configuration, device registry, enrollment and operational identity bytes and ACLs in ProgramData/LocalService, plus preexisting historical QA records. New operation-specific lifecycle evidence and log entries are separate from protected retained data; this clarifies the old impossible whole-tree-byte-identity wording while retaining the data-preservation requirement. No new record may overwrite archived historical evidence.

QuietUninstallString currently includes --remove-data in both baseline and history. Proposed contract: silent and standard uninstall preserve data; destructive removal requires its own explicit operator request and validated roots. No registry value is changed by this document phase.

Interactive-user Agent state and Electron profile retention need an explicit supported inventory before any cleanup extension. Service identity, environment schemas and peripheral configuration remain protected.

### 5. Agent shutdown and install/update boundaries

The existing service stops Node with Process.Kill, ignores its error, and waits without a deadline in that branch. Agent Job assignment happens after Node starts. Safe shutdown acknowledgement, outstanding operation policy, bounded fallback and child-assignment races need lifecycle design and disposable evidence. No change to RAW/GDI, XP-80 commands, drawer pulses or ROCHI protocol is permitted.

Install/repair/update must preserve the existing service account, QA target and identity, verify payload/version/health parity and retain a supported rollback path. No remote auto-update or database migration is introduced.

#### 5.2 HU-WIN-UPDATE-SPLIT: phased UPDATE contract

**Read-only source findings that motivate the split** (baseline HEAD `6a26df541e00703e1fffb02ea73afb36c628fee2` plus the current uncommitted working tree):

- `rollbackPOSPayload` in `installer_core_events.go` removes the whole POS install root when `POSPreviousPresent` is false, and `installWithObserver` sets that flag only for admitted REPAIR. Reusing `emitRollback` for UPDATE could delete the source POS payload.

**Mandatory preservation contract for every phase**

UPDATE SHALL preserve, and SHALL verify by digest/presence without logging contents: the LocalService installation ID, device registry, `CurrentUser` DPAPI secret blobs, the external Agent config including enrollment trust fields, the LocalService service account and the expected owner/DACL baseline of the managed roots. UPDATE SHALL NOT write, copy, re-protect or reset those files; an existing config is verify-only during UPDATE. Copying secret material into a backup requires its own approval and is not part of this contract. Because UPDATE never writes protected state, any digest change is a stop condition that yields `PARTIAL` and operator recovery, not an automatic restore. The source Agent and POS payload directories SHALL be retained unchanged until postcheck PASS; deleting old versions is a separate future retention task bound to the ROOT-05 gates. Staging directories are created absent and retained as evidence on failure; UPDATE adds no new path-walk deletion.

The durable update record SHALL live outside every replaced payload path and outside the LocalService profile, in an installer-owned location whose SYSTEM/Administrators-only security is established at creation and verified on re-read. It records operation ID, source/target identities, protected-state digests, service binary/account, registry values, junction targets, ACL baseline SDDL and journal step. **UPDATE ordering and rollback**

Only that proof reports rollback PASS; otherwise the record ends `PARTIAL`/`UNKNOWN` with both payloads retained. No auto-retry. #### 5.3 Native transition evidence contract (manus-update-evidence/v1)

The observer in `install_transition_evidence_windows.go` reads only, through the P0-B read-only boundary (`installAdmissionIO`), and produces the `installTransitionEvidence` that the 14.4a policy cross-checks against an exact allowlist entry. Every digest is SHA-256 in lowercase hex.

- **Agent payload digest:** `installTransitionPayloadDigest` over every regular file of a version root, with paths relative to that root (case-insensitive, order-independent, size and content bound). Installed: every file under `VersionsRoot\<installed version>`, which the installer fills with the embedded bundle plus `ManusTerminalSetup.exe` (the Agent config is only seeded there and copied to ProgramData). Candidate: the P0-B candidate inventory under the target `VersionRoot` (embedded bundle plus this executable).
- **POS payload digest:** the same over the POS version root. Installed: the directory the POS current junction targets, which must be a direct child of `POSVersionsRoot` whose name is a valid version. Candidate: the P0-B candidate inventory under the target `POSVersionRoot`, already checked against the embedded `pos-manifest.json`.
- **Candidate artifact SHA-256:** the digest of the running installer executable (the inventory entry for the target `ManusTerminalSetup.exe`).
- **QA environment digest:** SHA-256 of `manus-qa-environment/v1`, then the normalized enrollment endpoint (`https`, lowercase host, no trailing slash, no user info, query or fragment), the enrollment audience and the operator-provisioned signing key ID, one per line with a final newline. It is read from the retained host config `ConfigRoot\agent.config.local.json`, which UPDATE preserves. The candidate package must carry the same endpoint and audience and no trust fields (packages never embed trust). The public key, DPAPI material and every secret stay out of it.

An allowlist entry pins source and target artifacts, the candidate artifact SHA-256, the LocalService account and the QA environment digest. It is valid for any host enrolled in that environment with that exact source payload; host identity is protected separately by the installation ID and protected-state digests the executor records before it stops the service. Missing, unreadable, reparse-point, ambiguous or inconsistent input fails closed. The assumption that an installed version root holds exactly the bundle plus the installer executable (no runtime-written files) is verified only on the 14.4c VM; if it does not hold, admission rejects rather than guessing.

#### 8.4 Traversal, races and outcomes

The first implementation models one regular direct-child file. Proposed controller bounds: 5-second soft budget per object, 30-second operation budget, maximum two preparation attempts, existing 128-page/4096-child enumeration bounds, later recursion depth at most 32. These bound scheduling/retries, not a guarantee of cancelling synchronous kernel calls. Check monotonic deadlines between calls; on pending I/O, unexpected status, long call, sharing/identity error or uncertain prior disposition, stop further work. A hard watchdog/cancellation guarantee needs a separately authorized runner/process design; do not kill processes from this seam. No automatic disposition retry after uncertain success. These use the existing result vocabulary and do not imply current durable-result implementation. API acceptance, mark-pending, an empty-looking failed scan or a journal alone can never become `completed`. Fixture completion cannot certify product uninstall completion.

#### 9.5 State machine and recovery

Target effects mean service stop/delete and payload/data/registry mutation. Authorized staging/record work is separately accounted for and cannot be silently cleaned or called completed. Internal modeled progression: proposed -> authorized -> reserved -> claimed -> accepted/pending -> running -> completed. authorized/reserved/claimed are not public cleanup success; no reservation may issue an execution receipt before the H-bound claim is committed. Externally rejected/failed/partial/completed use the existing lifecycle result vocabulary; accepted/pending is nonterminal. The fake-only model labels all decisions simulated and returns no mutation permit or real completed result.

| Event | Required outcome / recovery |
|---|---|
| Missing authority, SID/session/logon mismatch, bad peer/mode/nonce, expiry | rejected before effects; no new claim or upgrade of a winner; preserve all data |
| Technical failure after valid approval but before any possible target effect | failed; release reservation only after proving no active owner/effects; otherwise retain unresolved claim |
| Helper accepted before ACK is received; either side crashes | accepted/pending remains discoverable; no re-execution from missing ACK; reconcile protected authority and retained worker identity |
| Parent does not exit, OpenProcess denied, wait timeout | no service stop/delete; report failed when no effects are proved, otherwise partial/unknown |
| Any actual/possible service stop/delete, file or registry effect with later failure | partial; list confirmed effects/unknowns; no assumed service/file rollback |
| All required process, service, payload, retention, registry and TEMP postconditions known and final result durably persisted | completed; cmd.Start, ACK, scheduling cleanup, successful API return or write attempt alone is insufficient |
| Corrupt/torn store, concurrent replay, power loss, logout, reboot, missing authority | fail closed; no stale-time takeover or reuse of old offers. Old accepted/running claims stay unresolved until current worker inactivity and exact installed state are independently proved |
| Retry after recovery | Fresh operation/approval, current generation/root/process evidence and exclusive claim. Retain historical records; never resume uncertain mutations from journal or recreate deleted files |

A crash with unknown effects cannot be retroactively labeled failed/completed. Terminal records are immutable; recovery creates a linked new reconciliation record rather than regressing terminal state. Reboot invalidates live-token/handle/monotonic receipts; a trustworthy native boot/authority epoch mechanism is still unselected. Fake epochs do not prove OS boot identity. A completed operation can be reported historically without authorizing another one. Idempotent no-op completion requires complete current absence and retention observations, matching installation scope and no unresolved active worker. TTL expiration never proves worker death.
